# Signed releases and verified installation

Release signatures use GitHub Actions OIDC and Cosign v3.1.4. Signing creates an
ephemeral key and short-lived Fulcio certificate, with transparency evidence in a
Sigstore bundle. There is no persistent release signing key, GitHub signing-key
secret or hardware-key requirement. A security key enrolled in a chat account is
unrelated to this GitHub workflow.

Production binaries never download, smoke-run or apply in-process updates or
rollback executables. Apply/rollback HTTP requests are refused even with the old
`ARTEX_ENABLE_SELF_UPDATE=1` flag; startup rejects that flag. Pre-existing unsigned
staging/marker files are ignored and preserved for operator inspection. The old
staging implementation remains only for real Go test fixtures. Normal server
restart signals still work. Read-only version information points to
`jaysonguglietta/artexV2`; it does not authorize installation.

## Trust policy

[scripts/signed-release.py](../scripts/signed-release.py) fixes these expectations
in reviewed source, not in downloaded metadata:

- Repository: `jaysonguglietta/artexV2`.
- Workflow: `.github/workflows/release.yml` in that repository.
- OIDC issuer: `https://token.actions.githubusercontent.com`.
- Release certificate identity: the exact workflow URL at `refs/tags/vX.Y.Z`.
- Expected source commit: an explicit full 40-character SHA supplied by the verifier.
- Expected run ID/attempt: supplied from the independently reviewed Actions run.
- Container names: `ghcr.io/jaysonguglietta/artexv2/application`, `/worker`, `/broker`, `/postgres`,
  always verified at an explicit `sha256` digest.

The verifier checks certificate repository/ref/SHA/event extensions as well as the
exact identity and issuer. It never accepts an artifact-supplied repository,
identity regexp, alternate issuer or custom CA/trusted-root override. It does not
skip certificate transparency or Rekor verification. Inherited `COSIGN_*` and
`SIGSTORE_*` overrides are stripped, preventing environment-selected keys, custom
roots or insecure flags. Cosign uses its official
Sigstore trust material; unavailable verification services/material fail closed.

Signatures prove this workflow signed particular content. They do not prove code
correctness, replace review, or defend against a compromised trusted workflow,
maintainer, GitHub/Sigstore service, runner or developer machine. The signed
provenance is an in-toto statement with the SLSA v1 predicate shape, generated by
this workflow; **no independently isolated SLSA builder or certified SLSA level is
claimed**.

## Publication gates

The [release workflow](../.github/workflows/release.yml) publishes only for a
protected semantic version tag, such as `v1.2.3`, when the repository variable
`ARTEX_ENABLE_RELEASES` is exactly `true`. It checks the exact repository/workflow,
checkout SHA, tag commit, current remote tag and ancestry in `origin/main`. Branch
or pull-request publication is refused. Ordinary source pushes do not publish.

An operator must configure appropriate protected-tag rules before opting in; the
workflow does not create repository settings or bypass a missing protection rule.
Protect `main`, require successful review/checks, restrict release-tag creation and
consider GitHub immutable releases. Those hosted settings remain operator policy,
not properties inferred from a YAML file.

Before a release build, reusable preflight workflows run the full Go/PostgreSQL,
frontend and live worker/Compose tests plus the image-security gate. Candidate
rehearsals run their own focused checks without publishing. The release workflow
builds five binary ZIPs. It builds application/worker/broker/postgres images
for Linux amd64 and arm64 and scans every component/architecture before pushing
any image. The PostgreSQL derivative retains the digest-pinned upstream engine
and replaces its obsolete privilege helper with the native Alpine helper. Its
exact derivative image is scanned, published and signed alongside the other
three components. The scanner fails on active
High/Critical/UNKNOWN issues, stale/incomplete evidence and unsupported/EOL OS;
review [image security](IMAGE-SECURITY.md) for exact policy.

Image publication uses only version/architecture tags and signed immutable index
digests. Before index creation, each uploaded architecture manifest is retrieved
by immutable digest from the fixed GHCR repository and its bounded JSON bytes
are hash-verified. Its config digest must match the authenticated scanned config,
which commits to exact OS/architecture and ordered rootfs diffIDs. A Docker 29
single-platform index is normalized to its verified leaf manifest. Foreign URLs,
inline descriptor data and invalid descriptors are refused. The final index is
also retrieved and hash-verified, with exactly the two approved platform/digest
pairs. Config/rootfs identities and publication bindings are retained in the
signed scan summary and therefore bound by provenance. Registry JSON requests
refuse redirects; no remote config/CDN blob is trusted in place of the scanned
config identity. Short-lived registry bearer tokens are refreshed for each check.

These checks also prevent a separate registry writer from racing a version tag
between upload and signing to substitute an unscanned config. Docker's push
digest is preferred over a tag lookup; any lookup fallback undergoes the same
immutable content/scan binding. A malicious registry writer can still remove
content or deny availability. Existing version tags/releases are refused; no mutable `latest` tag or
asset overwrite is used. Registry tags remain human-readable pointers: deployment
must use the verified digest, because an authorized external registry writer could
otherwise move a tag. A failed signing job can leave version images without valid
signatures; consumers must refuse them. Publication retry must investigate partial
state rather than overwrite it.

The signing job signs each component index digest, `SHA256SUMS` and
`provenance.json`, then verifies the result. Checksums bind every binary archive,
`images.json` and scan summary. Provenance binds their hashes, container digests,
repository, workflow, source ref/commit and run. The separate publication job
verifies again before creating a draft, uploading all assets without overwrite and
publishing it. Draft-first supports immutable GitHub releases when that repository
setting is enabled. New releases are explicitly not marked `latest`.

Permissions are job-specific: builds have read access; container publication and
signing have package write access; only signing jobs request OIDC; only the final
release publication job gets repository content write access. Actions and tool
versions are pinned. Signing credentials/tokens are never release assets.

## Verify before installation

Use a trusted checkout of the verifier and a reviewed Cosign v3.1.4 installation.
Do not execute a verification script fetched only from the same unverified release.
The pinned official installer action and its embedded platform checksums are linked
below. Review the intended tag, source commit and successful workflow run directly
in the expected repository.

Download the release's five ZIPs, `images.json`, `image-scan-summary.json`,
`SHA256SUMS`, `provenance.json` and all `.sigstore.json` bundles into one private,
otherwise empty directory. Do not unpack or run the binaries first. Then run, with
actual reviewed values replacing the examples:

```sh
python3 scripts/signed-release.py verify \
  --directory ./downloaded-release \
  --tag v1.2.3 \
  --commit 0123456789abcdef0123456789abcdef01234567 \
  --run-id 123456789 --attempt 1
```

Verification requires the exact archive set and bounded regular files, authenticates
both metadata bundles, validates every checksum and provenance subject, and checks
the registry's component signatures at the signed digests. Unexpected files,
symlinks, duplicate/unsafe checksum paths, ZIP traversal/links/special files, wrong
identities and mismatches are rejected. Archives are inspected, never extracted as
a verification side effect. Archive size/count/expansion budgets are explicit.
Private packages require ordinary read-only registry authentication on the trusted
verification machine; do not pass credentials in logged command arguments.

Only after success, install the selected verified binary or redeploy the exact
verified component digests from `images.json`. Back up needed state first and
follow the [worker deployment guide](WORKER-ISOLATION.md). Rollback follows the
same process for a separately verified prior release. An older valid signature is
not automatic permission to downgrade: the operator chooses the expected tag and
commit deliberately. Keep the signed manifests and verification/run evidence.

## Safe keyless CI rehearsal

Manual `workflow_dispatch` on `main`, with `dry_run=true`, works without enabling
release publication. It builds a synthetic candidate ZIP and minimal scratch
image, using a pinned disposable registry bound to runner loopback. Real GitHub
OIDC/Fulcio/Rekor signatures are created for the checksum/provenance blobs and the
local image. The same strict verifier checks them while the registry is alive.

The rehearsal then proves rejection of tampered signed bytes/ZIPs, wrong workflow,
repository identity, issuer, ref and commit, and even correctly signed provenance
that claims another repository. Candidate certificates are bound to
`refs/heads/main`; candidate filenames/provenance/image policy cannot verify as a
version-tag production release.

No GitHub release, Git tag or GHCR package is created by this path. Its candidate
bundles and synthetic artifacts are uploaded to an immutable Actions artifact for
seven days. The local registry disappears after the job, so later blob checks can
use downloaded bundles, but full candidate image verification belongs to the CI
rehearsal while that ephemeral registry exists. Public transparency evidence
contains workflow identity/artifact digests; no private assessment evidence or
credentials belong in this test.

Local tests and workflow parsing are not substitutes for this real OIDC run. The
release-tag publication path also requires separate authorized release validation;
a successful dry run is not a claim that a real release was published or all
cross-architecture build/registry policies were exercised.

## Tests and operational checks

```sh
python3 scripts/test-signed-release.py
python3 scripts/test-release-publication.py
# Run by release.yml only with its real OIDC bundles/local registry:
python3 scripts/test-keyless-release.py dist/candidate
```

Local tests use temporary OpenSSL keys for actual positive/tampered-signature
checks and metadata/path/gate regressions. They do not pretend to reproduce the
Fulcio trust chain. The CI negatives exercise actual keyless verification without
exposing bypass flags in the production verifier. Go regressions build a real
non-test production probe and prove unsigned staging/rollback cannot reactivate,
including with the legacy environment flag. Legacy staging unit fixtures remain
available under true Go test binaries only.

Before a real release, check current image/advisory results, complete source tests,
tag/main protections, the identity/commit in the signing run and all verification
outputs. The workflow refuses ambiguous/incomplete results. Keep external signed
verification mandatory rather than reintroducing a checksum-only updater.
